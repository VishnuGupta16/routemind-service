High-level design

The system, and where the model sits

One Spring Boot service over Postgres. The important property is the boundary: every number is computed in Java from SQL before the model is called, so the model can phrase an answer but never produce one.

Low-level design · detection

Deciding a metric is degrading

The window is split into six buckets and asked two questions — is it drifting, and did the last bucket break from the run before it. Then a second gate asks whether it is close enough to the target to matter, which is what separates a signal from noise.

Thresholds

// normalised so positive always means worse
worsenSlope = higherBetter ? -slope : slope
worsenStep  = higherBetter ? (runMean - last)
                           : (last - runMean)
stepZ       = worsenStep / runSd

// sub-noise wiggles are not signals
meaningful  = max(0.5, level * 0.02)

// and the at-risk band is PROPORTIONAL
margin = min(atRiskMargin, |target| * 5%)

A flat 2.0-unit warning band is 2% of an OTA target and 41% of a rating target. One setting, wildly different meanings — which is how a healthy metric got flagged at risk.

Low-level design · root cause

Decomposing the drop

Shift-share decomposition. For each slice: how many extra late trips it added versus the prior window, converted into the points of total OTA it explains. Additive, so the drivers rank and sum back to the headline.

Verified against raw SQL: 214,912 trips, 97.06% July OTA, prior window 210,419 / 95.41%, reason mix TRAFFIC 42.6→44.8, DRIVER 33.2→30.9, EMPLOYEE 24.3→24.4. Every figure in this deck matches the database to the digit.

Low-level design · chat

A question, end to end

The model is consulted three times and never for a number: who is asking, which analysis answers it, and how to phrase the one-line reply. Everything between those is Java over SQL.

The SQL fence

1Read only. A single leading SELECT/WITH; one statement.
2Allow-listed tables. No catalogues, no pg_*.
3Pre-filtered. Period and business unit bound by us — the model cannot widen its own slice.
4Bounded. Row cap and query timeout.
5Two attempts. Then answer from the API facts and say so.

14 unit tests hold this fence, including the regex bug that would have rejected every valid query — silently disabling the fallback entirely.

Low-level design · delivery

Scheduling and alerting

The scheduler ticks on a fixed interval and reads when from the database, so a cadence changes from the UI rather than a redeploy. Alerts land in the app, so the whole loop runs with no mail server.

What runs

Dedupe

One live alert per persona + unit + headline + day. Re-triggering replaces what is on screen rather than stacking a copy, so the UI button is safe to press twice.

Channels are plugins

Subscriptions reference a channel by kind(), never an address. IN_APP is always available; EMAIL reports itself unavailable rather than throwing.

Operating the model

What the LLM costs, and where

sarvam-105b is a reasoning model: it emits a chain of thought before any answer, and that thinking is billed against max_tokens. Budgeting only for the answer length made every reply return finish_reason: length with content: null — indistinguishable from "no model configured".

Measured, per call

Routing and persona are pure functions of the question text, so the same question never pays twice. The narrative is keyed on the numbers themselves. Only a real answer is cached — caching a fallback would pin the endpoint to template text for the life of the process after one transient failure.

07
Extension points

Adding to it without editing it

Three SPIs and a config file. A new metric, a new report and a new delivery channel are each one class; a new tenant is neither.

Everything degrades

No LLM key → template narrative. No SMTP → in-app only. No Kafka → historical-pattern prediction. The demo runs end to end on a laptop.

Virtual threads

The workload is blocking I/O, so each request gets a cheap virtual thread and the connection pool — not the thread pool — is the real limit. JEP 491 removed the JDBC pinning that made this counterproductive.

Tested where it matters

166 tests. The SQL fence, the alert band, the persona routing and the trend maths are all pinned — they are the parts where a silent wrong answer is possible.
